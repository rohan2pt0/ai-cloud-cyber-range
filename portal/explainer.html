The core mechanism

How a single prompt is handled

Every request passes one choke-point — the guardrail gateway. It blocks attacks on the way in, classifies the data, routes it to a model that is allowed to see it, then cleans the reply on the way out. This is the one picture that explains the whole estate.

The shape

Five pillars, one shared spine

Not five disconnected projects — five faces of one estate. They share identity, the data-tier rule, the AI gateway, secrets, observability and the audit trail. That shared spine is what lets a new project plug in later without rebuilding anything.

Seeing it work

A real attack, and a real banking query

The same gateway blocks an attack and lets legitimate work through untouched. This is the test that runs on every commit — 100% of attacks defended, zero false positives.

Prompt injection + secret exfiltration

SECRET-aws — credential pattern in text (LLM02)

Legitimate query with customer PII

"My PAN is ABCPE1234F — what documents
 do I need to complete my KYC?"
PII-PAN — redacted to [INCOME_TAX_PAN_REDACTED] before the model sees it
Intent is benign — the business question is answered
✓ ALLOWED · PII scrubbed · answer returned

Aadhaar and card numbers are verified with their real checksums (Verhoeff and Luhn), so a random 12-digit string is not mistaken for an Aadhaar — that is how false positives stay at zero.

Why one bypass isn't a breach

Defence in depth — 17 controls, not one wall

A single model will eventually be fooled, so the estate never relies on one control. Each layer catches what the layer before it missed; a bypass of one is caught by the next. Every control is mapped to the risk it answers.

Never a dead end

When a piece breaks, SecuRAX steps down — it doesn't stop

Every layer has a fallback, and ./securax up repairs what broke. The product is tested the way you use it: a sandbox installs it fresh, drives a real browser, kills components mid-flight and checks that chat still answers.

model ladder

Cloud → cloud → local

Gemini, Groq, OpenRouter (your free keys) in order; your private local model is the always-works floor.

elastic

self-healing

Router or gateway killed? Broken Llama Guard? Config missing? up restores and waits for READY.

Built like a seed

From a dormant seed to a multi-tenant forest — and back to sleep

Every stage is already defined as code in this repository (the genome). Nothing above the seed runs or bills until you grow it; hibernation keeps its data; waking restores it. Growth is reversible, and the only destructive verb is a deliberate one.

seed · crawl

Your laptop

Guardrail gateway, model router, chat, Guiding Map. ./securax up

sprout · walk

Always-on core

Keycloak, OpenBao, S3, Prometheus + optional Wazuh / MISP / TheHive. ./securax grow sprout

burrow · run-

Your own hardware

Real k3s on 1–3 machines, optional GPU node, power-cut reflex. Rehearsed on a Docker twin first. ./securax grow burrow

range · OSCP

Sleeping AD lab

GOAD pinned + lifecycle verbs; tells you which lab fits your RAM. ./securax range soil

tree · run

One cloud VM

k3s + Argo CD, state on a persistent encrypted disk, no open ports.

canopy · run+

Managed Kubernetes

EKS Auto Mode / GKE Autopilot / AKS: nodes follow pods, down to zero. Policy, runtime detection, backups.

forest · fly

Multi-tenant

One 5-line file stamps a tenant cell: namespace, quota, zero-trust, gateway, metering, own key + bucket.

./securax stages shows what is awake, hibernating or dormant. Dormancy is proved, not promised: offline Terraform plans show a sleeping estate contains only its seed bank (vault, key, data disk, budget alarm), and a real-container test sleeps and wakes the core with its data intact. Cloud stages plan only unless you pass --apply. Honest limits (nothing has been applied to a real cloud yet): docs/securax/29-LIFECYCLE-SEED-TO-FOREST.md.
