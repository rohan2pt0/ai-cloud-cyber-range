# Gap assessment — Post-quantum cryptography: NIST FIPS 203/204/205, NIST IR 8547 (draft) and the RBI Q-SAFE committee

> Post-quantum cryptography readiness of this estate, assessed against what the estate demonstrably does. Based on the NIST post-quantum standards (FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA), NIST's draft transition plan (IR 8547) and the scope the RBI has given its Q-SAFE committee (cryptography inventory / CBOM, crypto-agility, most-exposed systems). Not a regulator's checklist: RBI has not issued quantum requirements yet.

Source: [Post-quantum cryptography: NIST FIPS 203/204/205, NIST IR 8547 (draft) and the RBI Q-SAFE committee](https://csrc.nist.gov/projects/post-quantum-cryptography) — FIPS 203/204/205 final 13 Aug 2024; HQC selected as a backup KEM Mar 2025; IR 8547 initial public draft Nov 2024; RBI Q-SAFE committee press release 25 May 2026; read 2026-10-14. The FIPS dates are NIST's. IR 8547 (deprecate RSA/ECC after 2030, disallow after 2035) and FIPS 206 (FN-DSA) status come from secondary sources and are DRAFTS: verify at csrc.nist.gov. The RBI committee had not reported when this was written; nothing here is an RBI requirement. Status is our own judgement.

Applicability scope: all layers / categories (use `--category` to narrow).

**Software-scope coverage: 50.0%** of 13 requirements software can address (✅ 4 supported · 🟡 5 partial · ⬜ 4 gap), plus **3 obligations that belong to the regulated entity** (🏛, never counted as covered by software) and 1 not applicable (➖).

> This is **not** a compliance certification and a tool cannot make an entity "100% compliant"; it shows what the estate demonstrably does, what it does not, and what only the entity can do.

## Backlog — what to build or fix, highest priority first

- ⬜ **SIG-1** (medium) Post-quantum signatures / certificates (ML-DSA, FIPS 204) — Certificates and the private CA are ECDSA P-256. A signature is forgeable only while the algorithm is broken (never retroactively), and browsers and CA tooling do not yet accept ML-DSA certificates, so this follows rather than leads. **Next:** Issue a hybrid or ML-DSA estate CA once OpenSSL tooling and browsers accept it; keep the algorithm a single setting in governance/tls.py.
- ⬜ **VPN-1** (medium) Remote-access tunnel with a post-quantum handshake — Tailscale / WireGuard use Curve25519; a standard post-quantum WireGuard handshake does not exist yet (a pre-shared key mixed into the handshake is the interim mitigation). The estate does not run the VPN. **Next:** Document the pre-shared-key option and keep sensitive traffic on the local network.
- 🟡 **AGI-1** (medium) Crypto-agility of caller authentication (JWT / OIDC) — The gateway verifier accepts RS256 (RSA, quantum-vulnerable for signatures) and HS256 (HMAC-SHA-256, quantum-safe with a long secret) and only the algorithms the operator allows. There is no ES256/EdDSA path and no ML-DSA path yet, so moving needs a verifier addition, not just a setting. **Next:** Add ES256 and EdDSA; add ML-DSA when identity providers issue it. Prefer HS256 with a 256-bit secret for service tokens meanwhile.
- 🟡 **HNDL-1** (medium) Data with long confidentiality horizons is identified and kept off recordable paths — Classification-aware routing keeps RED data local and the residency guard restricts regions. Nothing yet labels data by how long it must stay secret. **Next:** Add a retention-horizon label to the data classes and let `crypto` list which classes cross an unprotected path.
- 🟡 **SIG-2** (medium) CA lifetime does not outlive the NIST draft disallow date (2035) — The estate CA is valid for 10 years, so it expires after 2035, the date NIST's draft proposes for disallowing P-256. `./securax crypto` flags it from the certificate itself; the CA is private, so the reissue date is ours to choose. **Next:** Shorten the CA validity or schedule its reissue before 2035; track in the rhythm.
- ⬜ **FIPS-1** (low) FIPS 140-3 validated cryptographic modules — The estate uses the OpenSSL builds inside its images without the FIPS provider enabled. **Next:** Document which images would need a FIPS provider and whether a validated build exists for them.
- ⬜ **SIGN-1** (low) Release provenance signatures — SLSA attestations use Sigstore keyless signing (ECDSA P-256): quantum-vulnerable for signatures, third-party controlled, and not retroactively forgeable. **Next:** Follow Sigstore's post-quantum signature work; nothing to change here.
- 🟡 **EGR-1** (low) Key exchange on calls to cloud AI providers — The router image that makes the calls offers hybrid key exchange (OpenSSL 3.5 or later, probed by `crypto`), but the provider decides what is accepted. Sensitive classes stay local by the data-tier router, so only what you accepted to send to a cloud travels. **Next:** Re-run `./securax crypto` after each router image update; record which providers negotiate the hybrid group.
- 🟡 **KEX-2** (low) Hybrid key exchange on the internal service-to-service hops — The sidecars use the same nginx build and group list, but the negotiated group is proven only at the edge. These hops never leave the machine, so harvest-now-decrypt-later is not the risk there. **Next:** Assert the negotiated group on a sidecar in the tls_internal journey.
